# Phase 7 — Athlete comparison (feature request 2026-10-03)
**Agent:** web-builder

## Goal
A page on which a visitor selects two or more athletes and compares them: key figures side by side, rating over time in one chart, seasons, direct bouts and common festivals.

## Exit criteria
- `compare.html` (linked from the navigation and from athlete profiles): select athletes through the existing search, selection kept in the URL (shareable), works from a sub-path with relative URLs, phone width.
- Side-by-side figures per athlete: current rating and rank, peak rating and date, career span, bouts, won–gestellt–lost, club, Teilverband, birth year; inactivity and identity-uncertain markers as elsewhere.
- One ECharts chart with all selected careers over time (1 April reversion not attributed to a festival, as on the profile).
- Season table (season-end rating and place per athlete and year, respecting burn-in / thin seasons and the 12-bout rule).
- Head-to-head: direct bouts between the selected athletes with tally and list (festival, date, Gang, result, grades), and the festivals both attended.
- Exported data stays deterministic; initial payload of the other pages does not grow noticeably; per-athlete data loaded on demand.
- Publication rules hold: withheld athletes (`publish_min_age`, unknown birth year + recent debut) are not selectable and never appear by name, id or rating in any new data or view; leak check over the real build passes; deploy guard and `noindex` cover the new page.
- Tests: JSON contracts, privacy, page checks, browser smoke test includes the new page.

Building the rows takes about 1.7 s.
  - **Chosen: (C), grouped variant → `data/bouts/bouts_<athlete_id>.json`**, loaded only by `compare.html`, one per selected athlete. Start page, profiles, festival pages and `meta.json` are unchanged. Cost: + about 6,306 files / 36 MB in `dist/` (Pages limit 1 GB) and about 2 s of build time. Common festivals need no new data: they are the intersection of the history files the page loads anyway for the chart.
  - **Contract:** `{"id", "opps": [athlete ids, sorted], "cols": BOUT_SIDE_COLS = ["gang","opp","res","g","go","flags"], "fests": [[fest_id, [row, ...]], ...], "other": {"cols": ["id","name","date","cat"], "rows": [...]}}` — `opp` is an index into `opps` of the same file (never into another file: a stale cached search index must not be able to name the wrong person); `res` from this athlete's side (1 won, 0 gestellt, 2 lost); `g` / `go` own and opponent's grade (null = "ohne Note"); `flags` = the festival files' bout flags plus `B_UNRATED = 16` (festival does not count for the rating); festivals in order (date, fest_id), rows by (gang, opponent id); `other` names the festivals of the file that are not in the athlete's history (unrated ones), so the page needs no festival index. Every published athlete gets a file, also an empty one (no 404 for a selectable athlete).
  - **Privacy rule of the file:** only bouts between two *published* athletes are written. Bouts against withheld, `not_a_name` and unrated ("ohne Wertung") opponents are left out altogether — the comparison never needs them, so no neutral placeholder row is exported and no withheld id, name, club, birth year or rating can be in the file. Indirect leaks considered: (1) the gap in an athlete's Gang numbers shows that he had another opponent there — the festival file already shows that bout with the neutral label, nothing new; (2) a head-to-head tally is only ever computed between two selected = published athletes, a withheld athlete cannot be a side of it; (3) the opponent index is file-local, so no positional reference into `athletes.json` can drift onto another person.
