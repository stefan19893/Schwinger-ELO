## Known inputs from Phase 5 review (2026-10-03)
- **Deploy by Pages artifact**, not by committing `dist/` (8,864 files, 51 MB; `actions/upload-pages-artifact` + `actions/deploy-pages@v4`). `dist/` stays git-ignored.
- **State between runs:** `data/raw`, `data/schwingen.db` and the Parquet files need a persistent store between scheduled runs (task 1). A cache miss must be treated as a **failure**, not as "start from scratch": a fresh runner without the cache would re-crawl everything (thousands of requests) or publish nothing.
- **Guard against an empty or shrunken site.** `build` already exits 1 without rating data (`build --allow-empty` is the explicit opt-in and must never be used in a workflow). In addition the deploy job should fail on `meta.empty` and compare `meta.counts` (athletes, ranked, festivals, bouts) with the `meta.json` of the currently deployed site, failing on a drop. This check belongs in the CLI, not in YAML.
- **`athlete_id` URLs are not stable.** Ids can change between runs (Phase 3) and the slugs fold ae / oe / ue and drop non-ASCII letters (e.g. `giger-samul-p878`). Decide the id scheme / a registry of issued ids before the site is linked publicly; today an outdated link lands on the not-found page with suggestions.
- **The JavaScript has no automated tests** (no Node / browser in pytest). Add a headless smoke test in CI: load the four pages against the built site, fail on the error banner (`#se-banner[data-error]`) and on an empty `#se-view`.
- **Owner decisions still open before any deployment** (do not deploy without them):
  - publication of ESV-derived data (results obtained via schlussgang.ch; ESV terms claim ownership);
  - 478 athletes born 2009–2010 are listed by name (345 of them ranked);
  - the only objection route is a public GitHub issue — consider an e-mail contact on `about.html`;
  - search-engine indexing: no `robots` meta tag and no `robots.txt` today, i.e. indexable once published.

- 2026-10-03 — **Task 1 done (web-builder): state persistence decided — one bundle file as an asset of a *draft* GitHub release, moved by `state-export` / `state-import`; a cold runner fails before the first request (`--require-state`).** Files: `src/state_bundle.py`, `src/cli.py` (`state-export OUTPUT`, `state-import SOURCE [--force]`, global `--require-state` / `SCHWINGEN_REQUIRE_STATE` for `crawl` and `all`), `tests/test_state_bundle.py` (13 tests). 990 tests green.
  - **What has to persist:** `data/raw` (540 MB, 4,182 cached responses), `data/schwingen.db` (157 MB), `data/processed` (15 MB), `data/published_meta.json` (guard baseline). **All of it is non-public material:** the cache holds the portrait JSON (birthdays, ESV licence numbers) and ~3,900 third-party PDFs, the database has the same fields (`portraits.birthday`, `hknr`, `city`) plus residences from the ranking lists, the Parquet files carry portrait slugs. Nothing of the state may become downloadable.
  - **Options compared** (GitHub limits as documented, from memory — not re-checked online today):
    | Option | Durability | Size limits | Who can read it in a public repo | First state from the owner's machine |
    |---|---|---|---|---|
    | Actions cache | **no**: entries unused for 7 days are evicted, LRU eviction above 10 GB per repo; a weekly cron that starts late, or the off-season, loses it | 10 GB per repo (about 16 generations of 0.5 GB with immutable keys) | workflow runs only — but including `pull_request` runs from forks, which can restore default-branch caches | **none** (a cache can only be written by a workflow run) |
    | Artifact chain (each run downloads the previous run's artifact) | **no**: retention at most 90 days, the off-season is longer; one failed link breaks the chain | generous | **any signed-in GitHub user** can download artifacts of a public repo | none without a seeding workflow |
    | Data branch | yes | 100 MB per file (the database is 157 MB), every update adds ~0.5 GB of history for ever | **everyone** | `git push` |
    | Public release asset | yes | 2 GB per asset | **everyone** | `gh release upload` |
    | **Draft release asset (chosen)** | yes: no expiry, no eviction | 2 GB per asset; the bundle is 504 MB and grows ~60 MB per season | only accounts with write access to the repository (a draft is not visible to others, has no public URL); fork PR tokens are read-only and cannot see it | `gh release create --draft` + upload, or drag and drop in the web UI |
    | Private store with a secret (private repo / bucket, or an encrypted public asset) | yes | — | nobody without the secret | script | 
    The last row is the only one that does not depend on a GitHub visibility rule, but it needs a secret; the brief asks for workflows without secrets, so it is the fallback if the owner does not want the state on a draft release.
  - **Residual risks of the choice (for the owner):** (1) pressing "Publish release" on the draft makes the bundle public — the release title says so, and every run first checks that the release is still a draft and fails otherwise; (2) the job that reads / writes the state needs `contents: write` (drafts are invisible to a read-only token) — the token is passed to the `gh` steps only, never to the pipeline steps, and the checkout does not persist credentials; (3) everyone with write access to the repository can download the bundle.
  - **Bundle** (`src/state_bundle.py`, format 1): gzip (level 1) tar with regular files only — `bundle.json` (format, creation time) first, `raw/**`, `schwingen.db` (snapshot through the SQLite backup API), `processed/*`, `published_meta.json` if present, `manifest.json` (size + sha256 of every file, row counts) last. gzip is worth it: 730 MB → 504 MB in 8 s. `state-export` refuses an incomplete state (so an upload can never replace a good bundle by a bad one) and writes `.part` + rename. `state-import` takes a file or a directory (newest bundle by creation time; unreadable ones are skipped with a warning), validates every member path (relative, no `..`, known top-level names, regular files only), unpacks into a staging directory inside the data dir, compares every file with the manifest and only then moves the parts into place; it refuses to replace existing state without `--force`. `sample/` and other directories are never touched.
  - **Generations instead of overwrite.** `gh release upload --clobber` deletes the old asset before uploading the new one; a failed upload would leave no state. The workflows therefore upload a new file name (`schwingen-state-<run id>-<attempt>.tar.gz`) and delete the older generations only afterwards; if the delete fails two generations exist and `state-import` picks the newer.
  - **Cold start = failure.** `state_problems(cfg)` (local files only): database missing, `festivals` or `bouts` empty, no cached response, or fewer than 90 % of the statistic PDFs of the known festivals in the cache. `crawl --require-state` / `all --require-state` log the reasons and exit 1 **before a client is created**; the tests count requests on a mock transport (0), also for `--portraits-only`, and check that not even an empty database is created. Without the flag nothing changes for local use.
  - **Run on the real data:** `state-export` 8 s → 503,903,468 bytes (8,373 files, 719 MB unpacked; festivals 2,037, bouts 491,676); `state-import` into a scratch dir 3 s; `diff -r` of `raw/` and `processed/` clean, all 13 tables with equal row counts, `PRAGMA integrity_check` ok, schema v6.
  - **Not verifiable here:** everything on the GitHub side — that `gh release download / upload / delete-asset / view` find a draft release by its tag with the workflow token, and the permission needed. The README names the check for the first manual run.
